# 회고록 — 2026-11-03

## 목표와 결과

nimf 지원을 UI에 명시하는 작은 문구 수정에서 시작해, 실제 원격 Caps Lock 전환 오류와 진단 도구를 함께 다뤘다.
최종적으로 사용자의 물리 키에서 평자음·영문 소문자 전환을 확인했고, 도크 위치 복구를 버튼으로 제공했다.
설정 적용과 패키지 설치도 완료했다.

## 잘못 판단했던 부분

첫 문구 수정은 저장소에만 적용했다. 실행 중인 설치본은 이전 코드를 사용하고 있었으므로 사용자 화면에 나타나지 않았다.
이후에는 설치 경로와 실행 PID를 확인하고 설치 파일의 내용 일치 및 재시작까지 검증했다.

키 매핑과 GSettings 읽기 확인만으로 즉시 실제 전환이 될 것처럼 설명했다.
합성 입력 66번이 성공해도 사용자의 실제 키는 원격 경로에서 230번으로 재등록될 수 있었다.
서버의 XKB Caps Lock 고정 해제만으로 Android 클라이언트의 변환까지 해결할 수 있다고 판단한 것도 충분하지 않았다.
사용자가 접속 경로와 실제 입력 결과를 알려준 뒤에야 클라이언트 쪽 키 매핑으로 문제를 좁힐 수 있었다.

입력 진단 UI도 처음에는 입력칸의 일반 키 신호만 관찰했다. 테스트 창의 성공을 실제 설치된 제어판에 그대로 일반화했다.
설치본에서 글자는 입력되지만 진단 표시가 비는 것을 확인한 뒤, GTK 창의 capture 단계와 포커스 필터를 사용하도록 수정했다.

## 효과가 있었던 검증

- 입력기 실행 상태, 저장된 입력기 백업, 설치본, 현재 키 매핑을 각각 확인했다.
- 전역 키 수집 대신 사용자가 명시적으로 선택한 입력칸에서만 진단했다.
- 합성 입력과 실제 물리 입력을 구분하고 사용자가 확인한 결과를 별도로 남겼다.
- Caps Lock 고정 상태와 Num Lock 보존, XKB 읽기 확인 실패, 원래 설정 복원을 테스트했다.
- Plank 재시작은 프로세스 시작 반환값만 보지 않고 새 PID와 실제 도크 위치도 확인했다.
- 전체 설치를 한 번 수행한 뒤 실제 설치 파일과 실행 화면을 확인했다.

## 다음 작업에 적용할 원칙

1. 입력 문제는 먼저 접속 기기 → 원격 클라이언트 → X11 → 입력기의 경로를 확인한다.
2. 설정 파일의 성공, 서버의 합성 입력 성공, 사용자의 물리 키 성공을 같은 결과로 보고하지 않는다.
3. GUI 수정은 실행 중인 설치 경로와 재시작 여부를 먼저 확인한다.
4. 키 매핑 변경은 백업·읽기 확인·원복을 함께 설계하고 다른 사용자 설정은 보존한다.
5. 원격 클라이언트에서 먼저 변환된 입력을 서버에서 계속 덮어 고치려 하지 않는다.
6. 세션 내 수정과 재로그인 후 유지 여부를 분리해서 기록한다.

## 제약

이번 확인은 특정 Android·Termux:X11·ThinLinc·Cinnamon·nimf 조합의 결과다.
다른 접속 기기나 EC 펌웨어, 물리 Fn 조합까지 지원을 검증한 것은 아니다.
